# ТЗ: «Умный мониторинг ИТ-инфраструктуры»

## Шаг 0. Описание кейса

**0.1 Назначение продукта**

Сервис-надстройка над существующими системами мониторинга (Zabbix, SolarWinds, Tibbo AggreGate, Saymon, Prometheus и др.), объединяющая их сигналы в единый управляемый поток оповещений.

**0.2 Принцип работы**

- Продукт работает поверх источников мониторинга, не заменяя их.
- Настройки источников (правила, триггеры) остаются без изменений.
- Продукт добавляет: приём событий в едином формате, приоритизацию, дедупликацию, маршрутизацию, эскалацию, элементы предиктивной аналитики.

**0.3 Состав результата**

Продукт должен:
- принимать событие от любой подключённой системы мониторинга в едином формате;
- определять, новая это проблема или продолжение уже существующей;
- приводить критичность события к единой шкале;
- группировать связанные события и подавлять дублирующиеся оповещения при массовых сбоях;
- доставлять сообщение о проблеме нужному человеку по заданному каналу;
- запускать эскалацию, если ответственный не отреагировал;
- позволять взять проблему в работу и закрыть её с фиксацией причины;
- фиксировать все действия в неизменяемом журнале аудита.

**0.4 Порядок разработки**

Путь одного события состоит из шести последовательных шагов:

```
1. Источник события → 2. Приём (Webhook/API) → 3. Классификация →
4. Дедупликация и защита от шторма → 5. Маршрутизация → 6. Работа дежурного
```

Каждый шаг реализуется и тестируется отдельно, до перехода к следующему. Минимальный работоспособный результат (MVP) — прохождение одного тестового события через все шесть шагов, от источника до дежурного, на одном источнике и одном канале доставки.

## Шаг 1. Источник события

**1.1 Источники интеграции**

- Zabbix
- SolarWinds
- Tibbo AggreGate
- Saymon
- Prometheus
- прочие системы мониторинга — добавляются по мере необходимости

Для старта: 1–2 источника (например, Zabbix + собственный генератор тестовых событий). Остальные добавляются позже по тому же паттерну интеграции.

**1.2 Способы подключения источника**

- **1.2.1 Push (агент).** Источник сам присылает данные при возникновении события. Пример: Zabbix через webhook-медиатип отправляет POST-запрос при срабатывании триггера.
- **1.2.2 Pull (без агента).** Платформа сама опрашивает источник по расписанию. Пример: SNMP-опрос сетевого оборудования.

**1.3 Требование к документации**

Для каждого источника фиксируется способ подключения (push/pull) — таблицей или аналогичной структурой в архитектурной документации проекта.

**1.4 Критерий готовности шага**

Источник (реальный или тестовый) формирует событие, готовое к отправке на Шаг 2.

## Шаг 2. Приём события (Webhook/API)

**2.1 Формат входящего события**

```json
{
  "source_system": "zabbix",
  "source_event_id": "8841203",
  "severity": "critical",
  "object": { "name": "db-prod-03", "type": "server" },
  "message": "Диск заполнен на 94%",
  "occurred_at": "2026-07-10T02:14Z",
  "tags": ["disk", "prod", "msk-dc1"]
}
```

Обязательные поля:
- `source_system` — источник события;
- `severity` — исходная критичность (приводится к единой шкале на Шаге 3);
- `object` — объект, к которому относится событие (нужен для группировки на Шаге 4);
- `tags` — метки для маршрутизации и фильтров.

**2.2 Точка приёма**

Один HTTP-эндпоинт (например, `POST /events`), принимающий событие в формате п. 2.1.

**2.3 Требование к нагрузке**

- Средняя нагрузка: ~1 событие/сек.
- Пиковая нагрузка (каскадный сбой): до 50× от средней.

**2.4 Асинхронная обработка**

- Эндпоинт приёма только принимает событие и кладёт его в очередь (например, Redis).
- Обработка события (Шаги 3–5) выполняется отдельным процессом/воркером, читающим из очереди.
- Приём и обработка не должны быть одним синхронным вызовом.

**2.5 Ограничение по источнику**

Лимит числа событий, принимаемых от одного источника за единицу времени. События сверх лимита — в очередь на отложенную обработку или в агрегат, не в прямую обработку.

**2.6 Критерий готовности шага**

- Единичное событие доходит до очереди.
- Пакетная отправка (сотни событий одновременно) не приводит к падению сервиса или потере ответа на запрос.

## Шаг 3. Классификация

**3.1 Правило классификации**

Таблица соответствий «исходная severity источника → критичность платформы», отдельная для каждого источника (например: Zabbix `severity: critical` → `CRITICAL`).

**3.2 Требование к применению правила**

Классификация выполняется автоматически при обработке события, без ручной разметки и без анализа текста сообщения.

**3.3 Критерий готовности шага**

События с разными исходными значениями severity после обработки получают корректный уровень критичности по единой шкале платформы.

## Шаг 4. Дедупликация и защита от шторма

**4.1 Fingerprint события**

```
fingerprint = source_system + object.name + monitor_name
```

**4.2 Логика создания/обновления проблемы**

- Fingerprint уже соответствует активной проблеме → проблема не создаётся заново, обновляются счётчик повторов и время последнего срабатывания.
- Fingerprint новый → создаётся новая проблема.

**4.3 Разграничение сущностей**

- **Событие** — неизменяемая запись в журнале.
- **Проблема** — изменяемая сущность со статусом (`активна` / `в работе` / `закрыта`) и историей. Пока объект не вернулся в норму, проблема остаётся одной и той же; меняется только её критичность.

**4.4 Группировка**

Группировка событий по общим тегам/лейблам, помимо точного совпадения fingerprint.

**4.5 Плановые работы (mute/downtime)**

- Режим «on demand», включаемый инженером перед плановыми работами.
- Привязка режима к конкретному объекту, не ко всей системе.
- В период действия режима события по объекту не доходят до дежурного.

**4.6 Защита от лавины событий**

- Лимит числа сообщений на одного получателя за единицу времени.
- Автоматический переход в режим одного сводного сообщения при превышении порогового потока событий от источника, вместо рассылки каждого события отдельно.

**4.7 Критерий готовности шага**

- Повторная отправка одного и того же события не создаёт новых проблем — растёт только счётчик у существующей.
- Массовая единовременная отправка разных событий приводит к срабатыванию лимитов/сводного сообщения, а не к рассылке каждого по отдельности.

## Шаг 5. Маршрутизация

**5.1 Формат исходящего сообщения**

```json
{
  "subject": "...",
  "text": "...",
  "priority": 0,
  "monitor_name": "...",
  "state": "CRITICAL",
  "prev_state": "OK",
  "object_id": "...",
  "resolved": false,
  "owner": "...",
  "created_at": "...",
  "count": 1
}
```

- `subject`, `text` — для получателя-человека.
- `priority`, `state`, `monitor_name` — для машинной обработки.
- `resolved`, `prev_state` — контекст изменения статуса без обращения к системе-источнику.

**5.2 Каналы доставки**

- Webhook — обязательный канал (через него подключаются внешние системы, включая мессенджеры).
- Mail — несрочные оповещения.
- Mattermost — командные каналы.
- Telegram — срочные оповещения.

**5.3 Интеграция с TrueConf**

- 5.3.1 Приём событий от TrueConf и отправка команд в него реализуются через **TrueConf Chatbot Connector** — API для чат-ботов.
- 5.3.2 Подключение — по WebSocket к службе **TrueConf Bridge** (TCP-порт 4309), с авторизацией по токену через OAuth 2.0 <cite index="6-1">перед отправкой запросов необходимо подключиться к WebSocket-серверу и авторизовать соединение идентификационным токеном</cite>.
- 5.3.3 Следствие для архитектуры: обработка ответов пользователя (нажатие кнопки/команда) требует постоянно работающего процесса-бота, а не публичного HTTP-эндпоинта, ожидающего вызова от TrueConf.
- 5.3.4 Для реализации на Python доступна библиотека <cite index="4-1">python-trueconf-bot, построенная по модели aiogram и позволяющая работать с Python-классами вместо сырых JSON-запросов</cite>.
- 5.3.5 Поддержка inline-кнопок в чат-ботах TrueConf <cite index="5-1">анонсирована как нововведение версии сервера 5.5.6</cite> — до проверки версии сервера в качестве резервного варианта закладывается ввод текстовой команды (например, `/take 8841203`) как эквивалент нажатия кнопки.

**5.4 Цепочка эскалации**

1. Личное оповещение исполнителю.
2. Нет реакции 10 минут → оповещение дежурного канала.
3. Нет реакции ещё 15 минут → оповещение руководителю системы.

**5.5 Дежурство**

- Таблица дежурств в БД: кто дежурит в текущий период.
- На шаге эскалации (п. 5.4) подставляется текущий дежурный из таблицы.

**5.6 Управление подписками**

- Личный кабинет для самостоятельного управления подписками на оповещения.
- Ролевая модель — стартовый набор прав по умолчанию, не жёсткая привязка подписок к роли.
- Автоматическое отключение подписок при увольнении/смене роли — через синхронизацию с кадровым каталогом, без ручных действий.

**5.7 Критерий готовности шага**

- Тестовая проблема доставляется адресату по заданному каналу.
- При отсутствии реакции в заданное время срабатывает следующий шаг эскалации.
- В сообщении эскалации указан реальный дежурный из таблицы, а не фиксированное имя.

## Шаг 6. Работа дежурного

**6.1 Жизненный цикл проблемы**

```
активна → Acknowledge (взята в работу) → [декомпозиция на задачи] → закрыта (с комментарием о причине)
```

- Acknowledge — обязательное действие, доступное как кнопка/команда.
- Закрытие проблемы без комментария о причине — недопустимо.
- Декомпозиция на несколько задач — при необходимости распределения между исполнителями.

**6.2 Обратная связь из канала связи**

- Действие пользователя в канале (кнопка или текстовая команда, см. п. 5.3.5) вызывает API и переводит проблему в статус Acknowledge.

**6.3 Журнал аудита**

- Каждое действие (Acknowledge, изменение настроек мониторинга, закрытие проблемы) фиксируется отдельной записью.
- Журнал допускает только добавление записей; редактирование и удаление запрещены.

**6.4 Критерий готовности шага**

- Действие пользователя в канале переводит проблему в статус «в работе» в БД.
- Закрытие проблемы без комментария технически невозможно.
- Каждое действие отражается записью в журнале аудита.

## Раздел 7. Дополнительные требования

Реализуются после того, как Шаги 1–6 работают на одном источнике и одном канале.

**7.1 Безопасность**

- Авторизация через корпоративный каталог (LDAP/AD, Keycloak); проверка учётных данных делегируется каталогу.
- Ролевая модель доступа: группа видит только относящиеся к ней показатели.
- TLS на всех интерфейсах и на API уведомлений.
- Синхронизация подписок с кадровым каталогом (см. п. 5.6).

**7.2 Хранение данных**

- Горячие данные — дни/недели, полная детализация.
- Более старые данные — агрегированные сводки для трендов и отчётности.
- Автоматическое удаление устаревших данных по TTL на уровне БД.

**7.3 Дашборд администратора системы оповещений**

- Число обработанных сообщений за сутки.
- Доля успешно доставленных сообщений и причины недоставки для остальных.

**7.4 AI-агрегатор**

Реализуется последним, после готовности Шагов 1–6.

- Модель — сменный компонент за API-контрактом: вход — вопрос и контекст события, выход — текстовый ответ. Допускается любая модель, включая локальную.
- Сценарии в один клик у записи лога: краткая справка, развёрнутый анализ, гипотеза причины, возможные последствия.
- Свободный текстовый запрос к модели.
- Поиск решений по базе знаний: сначала поиск релевантных документов по тексту, затем документы вместе с запросом передаются модели.
- Системный промпт (пример):
  > Ты — ассистент дежурного инженера. Дан текст ошибки и контекст объекта. Ответь по пунктам: 1) что произошло, 2) вероятная причина, 3) что проверить в первую очередь. Не выдумывай факты, которых нет в контексте.

## Раздел 8. Технологический стек

- **Backend/API:** фреймворк с быстрым стартом (Python + FastAPI или Node.js + Express) — реализация эндпоинтов Шагов 2–6.
- **Очередь (п. 2.4):** Redis.
- **База данных:** одна PostgreSQL для событий, проблем, подписок и аудита на старте проекта.
- **Логика дедупликации/группировки/маршрутизации (Шаги 4–5):** Prometheus Alertmanager — как референс модели конфигурации (routing tree, receivers, grouping, silences); использование готового компонента — по решению команды.
- **Админ-дашборд (п. 7.3):** Streamlit — быстрая сборка панели без отдельной frontend-разработки.
- **AI-часть (п. 7.4):** любая LLM с HTTP API, включая локальную модель через Ollama.

## Раздел 10. Риски

| Риск | Мера |
|---|---|
| Попытка поддержать все источники сразу | Ограничение на старте 1–2 источниками (п. 1.1) |
| Излишне сложная ролевая модель до появления пользователя | Стартовая модель по умолчанию, без усложнения (п. 5.6) |
| Демонстрация откладывается до полной готовности | Промежуточная демонстрация сквозного пути на одном источнике на раннем этапе |
| Отсутствие нагрузочного тестирования | Тест пакетной отправки событий на Шаге 2 (п. 2.6) до защиты проекта |

## Раздел 11. График выполнения

**Этап 1 (первые 2 дня):**
- Шаг 1 — источник и генератор тестовых событий.
- Шаг 2 — приём и очередь.
- Шаг 3 — базовая классификация.
- Шаг 5 (упрощённо) — один канал доставки без эскалации.

**Этап 2 (до конца недели):**
- Шаг 4 — дедупликация и защита от шторма.
- Шаг 5 — полная маршрутизация, эскалация, дежурства, self-service.

- Второй источник событий.
